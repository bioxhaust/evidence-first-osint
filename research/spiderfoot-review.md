Official README and source were read from GitHub. Upstream requirements were installed successfully into scratch/spiderfoot-venv on Python 3.12.11 / macOS arm64. `sf.py -V` ran; this alone is only a version check. Actual runtime validation additionally executed `sfp_spider`, `sfp_webserver` and `sfp_webanalytics` against four original localhost pages.

The standard CLI accepts seed entity types, not a URL with a custom port. For a controlled beginner lab the course therefore provides a transparent module-API adapter with a fixed LINKED_URL_INTERNAL seed and an event queue. It invokes actual upstream module methods and exports original event data/parents. It is explicitly **not the complete sf.py scanner**, UI, database/correlation engine or native full-scanner export. This avoids making a misleading claim about how the demonstration runs.

Observed runs: all three modules = 4 pages, 32 events, 2 analytics-token events; without analytics module = 4 pages, 30 events, 0 analytics events; maximum one page = 1 page, 12 events, 0 analytics events. Each fetched page used HEAD and GET. Both matched tokens exist only in copied HTML comments, useful for teaching why a regex match does not establish deployed analytics or ownership. The external `.example` link was recorded but never fetched.

In particular, event confidence defaults to 100; it is not independently calibrated in this lab.

Only these local paths were exercised. The crawler actively requests its own fixture. External services, API-key modules, full UI workflow and Gephi import remain untested. The Python socket guard restricts standard connect/resolve for the tested code path; it is not an OS sandbox. Upstream temporarily changes the Python HTTPS factory during initialization; the adapter restores it immediately and uses fixed localhost HTTP only. No installed upstream file is modified.
