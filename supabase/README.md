## Что нужно сделать владельцу проекта

Настройка выполняется один раз. Для существующего проекта выше создание проекта и применение миграции уже завершены; продолжение начинается с проверки URL и подключения GitHub. Полный порядок ниже сохранён также для отдельного развёртывания или форка. Все секретные значения вводятся только в панели соответствующих провайдеров; их не нужно отправлять в чат, Issues или репозиторий.

1. Войдите в [Supabase Dashboard](https://supabase.com/dashboard), создайте проект в выбранном регионе и дождитесь готовности. Если доступен подходящий бесплатный тариф, можно использовать его; квоты, паузы неактивных проектов и условия определяет провайдер. Пароль базы данных сохраните у себя.
2. В SQL Editor выполните [миграцию](migrations/202611030001_private_trainer_progress.sql) целиком. Она создаёт новую таблицу, проверки схемы, RLS и функцию сохранения с контролем версии. Это миграция для нового проекта: повторное выполнение уже применённой миграции намеренно не перезаписывает таблицу.
3. В Authentication → URL Configuration задайте Site URL и разрешённый Redirect URL: `https://bioxhaust.github.io/evidence-first-osint/trainer/`. Используйте точный адрес с завершающим слешем. Для локальной разработки добавляйте только нужный локальный адрес отдельно; не используйте широкую маску чужих доменов.
4. В Authentication → Sign In / Providers → GitHub скопируйте Callback URL. Он имеет вид `https://PROJECT_REF.supabase.co/auth/v1/callback` — это адрес Supabase, а не страница тренажёра.
5. В [GitHub Developer settings → OAuth Apps](https://github.com/settings/developers) создайте OAuth App. Название: `Evidence First OSINT`; Homepage URL: `https://bioxhaust.github.io/evidence-first-osint/`; Authorization callback URL: точный адрес из предыдущего шага.
6. Скопируйте Client ID и сгенерируйте Client Secret. Вставьте их только в настройку провайдера GitHub в Supabase, включите провайдер и сохраните. **Client Secret не является publishable key и не должен попадать в браузер.** Не добавляйте scope `repo` для входа в учебный курс.
7. После включения провайдера GitHub в Connect/API Keys проекта найдите Project URL и ключ **Publishable**, начинающийся с `sb_publishable_`. Внесите только эти два общедоступных значения в `docs/assets/trainer/config.js`; оставьте `authMethods: ['github']`. До этого шага сохраняйте пустую конфигурацию, чтобы не показывать неработающую кнопку входа. Старый JWT-ключ `anon` также распознаётся адаптером, но для нового проекта предпочтителен publishable key. Ключи `sb_secret_` и `service_role` запрещены.
8. Опубликуйте изменение конфигурации обычным workflow Pages. Проверьте настоящий вход двумя отдельными тестовыми GitHub-аккаунтами и сценарии ниже. До этой проверки не объявляйте облачную синхронизацию рабочей.

Секрет OAuth хранит Supabase. GitHub Pages получает только публичный ключ и адрес API. Доступ к данным обеспечивает RLS; скрытие публичного ключа не является защитой.

## Контракт frontend-адаптера

`cloud.js` экспортирует `createCloud(config, options)`, `CloudError` и `validateProgressState`. Параметр `options` нужен для тестирования; обычный интерфейс передаёт только конфигурацию.

```js
import {cloudConfig} from './config.js';
import {createCloud} from './cloud.js';
import {mergeProgress} from './progress.js';

const cloud = createCloud(cloudConfig);
await cloud.initialize();

// В обработчике осознанного нажатия кнопки входа:
// location.assign(await cloud.signInWithGitHub());

// После входа и при синхронизации:
async function sync(localProgress, allowedIds) {
  for (let attempt = 0; attempt < 2; attempt++) {
    const remote = await cloud.pull();
    const merged = remote ? mergeProgress(localProgress, remote, allowedIds) : localProgress;
    try { return await cloud.push(merged); }
    catch (error) {
      if (error.code !== 'CONFLICT' || attempt === 1) throw error;
    }
  }
}
```

Сохраняйте актуальную локальную копию при каждом ответе ученика, до сетевого запроса. Пока выполняется синхронизация, новые ответы могут появиться: интерфейс должен объединить её результат с **текущим** локальным состоянием, а не заменять его снимком на момент начала запроса. При переключении аккаунтов локальные копии должны быть раздельными по user ID; гостевой прогресс объединяется с аккаунтом только по понятному пользователю решению.

API адаптера:

- `configured`: можно ли обращаться к настроенному серверу. `authMethods`: разрешённые интерфейсом способы входа.
- `signInWithGitHub()`: возвращает URL авторизации с SHA-256 PKCE challenge; перенаправление выполняет обработчик кнопки.
- `initialize()`: обменивает callback `?code=` только при наличии соответствующего сохранённого verifier. Удаляет служебные коды из URL. Возвращает сессию либо `null`.
- `getSession()`: проверяет/обновляет сохранённую сессию при необходимости. `session()`: только текущая локальная информация без запроса.
- `onAuthChanged(callback)`: сразу передаёт текущую сессию и возвращает функцию отписки. Сессия имеет поля `{user:{id,email}, expiresAt}`; access/refresh tokens интерфейсу не выдаются.
- `pull()`: возвращает прогресс или `null`, запоминает revision. `push(state)`: сохраняет после загрузки и возвращает подтверждённое состояние. Вызов `push` до `pull` отклоняется.
- `signOut()`: немедленно удаляет локальные токены и затем отзывает текущую серверную сессию. Другие устройства не выходят. При сетевой ошибке локальный выход уже выполнен, но серверный отзыв не подтверждён; локальный прогресс не удаляется.
- `destroy()`: убирает таймер обновления и подписчиков при уничтожении интерфейса.

Ошибка `CONFLICT` означает, что другое устройство уже сохранило новую версию. Нужно снова загрузить состояние, объединить и повторить сохранение ограниченное число раз. Другие ошибки нельзя трактовать как пустой серверный прогресс. Адаптер не принимает решений о слиянии вместо `mergeProgress`.

## Данные, RLS и конфликтующие изменения

Таблица `public.trainer_progress` хранит одну строку на `auth.users.id`. Анонимной роли запрещены чтение, запись и вызов RPC. Авторизованной роли RLS разрешает только свою строку; изменение `user_id` на чужой также запрещено. RPC `save_trainer_progress` использует `auth.uid()` на сервере, а не идентификатор, выбранный клиентом. У функции `SECURITY INVOKER`, фиксированный пустой `search_path` и явные разрешения.

Состояние содержит только `version`, `completed`, `attempts`, `mistakes`, `activityDays`, `review`, `completedAt`: идентификаторы упражнений, счётчики, даты и признаки повторения. Произвольных заметок, исследуемых лиц, ссылок на расследования и ответов свободным текстом здесь нет. Обе стороны проверяют допустимые поля и лимит 128 КиБ; сервер проверяет типы даже при обходе интерфейса. Email и служебные данные входа обрабатывает Supabase Auth по настройкам владельца.

Функция сохраняет состояние только при совпадении revision. Поэтому два одновременных устройства не могут незаметно перезаписать друг друга через штатный клиент. Повторный запрос после конфликта должен использовать новое объединение. Прямой доступ авторизованного пользователя ограничен собственной строкой; правила не защищают пользователя от намеренного изменения его собственного прогресса.

`mergeProgress` объединяет завершённые упражнения и дни активности; берёт максимум счётчика попыток, а не сумму. Признак повторения выбирается по последнему времени. Часы устройства могут быть неверными, поэтому это удобный учебный прогресс, а не защищённая система аттестации. Контрольная версия БД предотвращает потерю записи, но не доказывает правильность времени устройства.

## Хранение сессии и PKCE

Токены хранятся в `sessionStorage` данной вкладки, с ключом, привязанным к URL проекта. При недоступном хранилище email-сессия остаётся только в памяти. Перезагрузка той же вкладки обычно сохраняет вход; закрытие вкладки или завершение сеанса браузера может потребовать входа снова. Некоторые браузеры восстанавливают sessionStorage при восстановлении закрытых вкладок, поэтому для явного выхода используйте кнопку «Выйти».

PKCE verifier создаётся через Web Crypto и хранится в sessionStorage перед перенаправлением. Без рабочего хранилища OAuth не запускается. Вернувшийся код обменивается вместе с verifier; неподготовленный callback отклоняется. После попытки обмена verifier удаляется, при сетевом сбое вход нужно начать заново. Один поток входа в одной вкладке за раз; не открывайте его промежуточные ссылки на другом устройстве. Чужие `#access_token` не принимаются: фрагмент очищается, требуется новый вход.

Access token обновляется перед истечением и перед API-запросами; параллельные запросы используют один обмен refresh token. Сбой сети не удаляет локальный прогресс. Как у любого статического JavaScript-клиента, исполняющийся код того же origin имеет доступ к sessionStorage: нельзя добавлять непроверенные скрипты или выводить пользовательский HTML через `innerHTML`. Этот адаптер не использует HTTP-only cookies и не заявляет защиту от XSS сам по себе.

## Необязательный вход по email

`signUp(email,password)` и `signIn(email,password)` доступны, если в `authMethods` добавлено `'email'`. Новый пароль должен содержать минимум 12 символов; серверные требования задаются в Supabase. Подтверждение email не отключайте ради обхода доставки писем.

На дату проверки **2026-11-03** документация Supabase указывает, что стандартный SMTP отправляет письма только адресам членов команды проекта, ограничен двумя сообщениями в час и не предназначен для публичной эксплуатации. Для регистрации внешних учеников по email нужно настроить собственный SMTP и домен отправителя. Конкретные квоты могут измениться. GitHub OAuth является основным вариантом без этой зависимости.

При обязательном подтверждении `signUp` возвращает `{requiresEmailConfirmation:true, session:null}`. После подтверждения письмом пользователь входит паролем; implicit-токены из URL не становятся сессией автоматически. Если включается email-вход, сопровождающий также должен определить поддерживаемый путь восстановления пароля: в текущем интерфейсе отдельная форма восстановления не реализована.

## Проверки перед объявлением готовности

1. Два отдельных аккаунта A и B: A отвечает на упражнение; B не получает этот прогресс и не может запросить строку A напрямую через REST.
2. Аккаунт A на втором устройстве получает сохранённый результат; новый ответ второго устройства виден на первом после синхронизации.
3. Одновременная запись вызывает контролируемый конфликт и повторное объединение; ранее завершённые упражнения сохраняются.
4. Отключение сети во время ответа оставляет локальный результат. После восстановления связи результат объединяется с серверным.
5. Выход удаляет локальные токены. Переключение A → B не переносит частный прогресс A в B автоматически.
6. Callback с отсутствующим/просроченным verifier не создаёт сессию. Вход GitHub не запрашивает scope `repo`.

На этапе подготовки кода выполнены **14 JS-тестов с синтетическими HTTP-ответами** (`node --test tests/cloud.test.mjs`) и **13 проверок реальной миграции/RLS в отдельном временном PostgreSQL 16.15** с имитацией `auth.uid()` и ролей Supabase. В сохранённом отчёте [qa-cloud-database.json](../research/evidence/qa-cloud-database.json) все 13 результатов имеют `pass: true`. Позднее миграция также успешно применена в SQL Editor действующего проекта `lwutttdgpwaqcyaxkkhf`; это отдельное подтверждение развёртывания схемы, а не проверка пользовательского входа.

Настоящий Supabase Auth, OAuth-провайдер, доступ двух разных аккаунтов и синхронизация двух браузеров после настройки GitHub ещё требуют проверки. Учётные записи реальных учеников в ходе локальных тестов не создавались. Локальный PostgreSQL-отчёт не переименован в проверку действующего Supabase-проекта и не приписывает ему непроведённые тесты.

Для повторения проверки базы на компьютере с установленными серверными утилитами PostgreSQL: `python3 tests/cloud_database.py`. Скрипт получает путь из `pg_config --bindir`; при необходимости передайте `--pg-bin` с каталогом утилит. Он создаёт отдельный временный кластер без TCP и удаляет его после остановки, не подключаясь к существующей базе.

## Эксплуатация и удаление данных

За регионом хранения, квотами, уведомлением о приватности, резервными копиями, доступом администраторов и настройками Auth следит владелец Supabase-проекта. Перед публичным включением он должен назвать используемого провайдера и способ обращения по данным аккаунта. Не просите учеников публиковать email в GitHub Issues.

Удаление пользователя через Supabase Auth удаляет строку прогресса по `ON DELETE CASCADE`. Самостоятельный серверный endpoint удаления аккаунта не входит в этот статический адаптер, потому что административный ключ нельзя помещать в браузер; на первом этапе удаление выполняет сопровождающий по согласованному приватному запросу. Локальные данные браузера управляются отдельно. Авторизация GitHub для курса может быть отозвана самим пользователем в настройках GitHub.
